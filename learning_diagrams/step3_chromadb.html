Chunks to an Index

step3_chromadb.py swaps Step 2's hand-rolled loop for a real index. Seven chunks go in once; every query after that is a graph walk, not a scan — with the same embedding function and the same cosine math you already trust.

Build once: seven chunks become an index

collection.add() is the expensive moment — it's the only place these seven texts actually get embedded (7 sequential Ollama calls). Everything after this line is a fast lookup against vectors that already exist.

What HNSW actually is

"Hierarchical Navigable Small World" is a fairly simple idea under the name: a sparse top layer for long jumps, a dense bottom layer holding every vector, and a greedy walk down through both. This is a schematic of that shape — not a dump of this run's actual graph, which lives inside Chroma's internals and isn't inspectable from Python.

One real query, top-2 neighbors, converted back to similarity

collection.query() returns Chroma's cosine distance, not similarity — smaller is better, the opposite of Step 2's intuition. 1 - dist converts it back. Traced here for the actual first query from this run.

Worth noticing, not yet proving This collection is in-memory only — chromadb.Client(), not PersistentClient — so it starts over from nothing every time the script runs; Step 6 is what makes the index survive a restart.

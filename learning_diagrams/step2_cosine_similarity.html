Vectors to a Score

step2_similarity.py takes the vectors Step 1 produced and turns a pair of them into one number between -1 and 1 — built entirely with math, no numpy. This scoring function is what every later retrieval step, ChromaDB included, is built on top of.

Embed once, compare four times

One query, four candidates — two written to score HIGH (same meaning as the query), two to score LOW (unrelated). The query is embedded a single time at L59 and reused for every comparison — embedding is the expensive network call, so it's never re-fetched.

The four numbers become a ranking

results.sort(reverse=True) sorts the (score, text) tuples by score, descending — Python compares tuples element-by-element, so putting the score first in the tuple is what makes this work with zero extra code. This is the actual terminal output from the run above.

What happens inside cosine_similarity()

Traced for one real pair — the query against candidate 1 — with the exact intermediate numbers Python computes but never prints.

Worth noticing, not yet proving zip(a, b) at L39 silently stops at the shorter of the two vectors if their lengths ever differ — no error, just a quietly wrong score. That never happens here because the same model produces both vectors, but it's the kind of bug that produces a plausible number instead of a crash. Next problem: comparing a query against every candidate by hand, one at a time, is O(n) — fine for 4 candidates, unusable for a real document store.

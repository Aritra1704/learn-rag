Splits to a Winner

step7_chunking.py takes the same 5-paragraph document and the same 250-character target size, and runs it through four different splitters — fixed, sentence-aware, paragraph-aware, recursive — then measures which one actually retrieves better. Every number below is real output from one run.

Same cap, four different shapes

CHUNK_SIZE = 250 is held constant across all four strategies — the controlled variable that makes comparing them meaningful. What differs is chunk count, size spread, and exactly where the cut falls.

Why paragraph-aware beats sentence-aware on one real query

Both strategies pack whole sentences under the cap — the difference is where they're willing to reset. chunk_sentences() runs across the entire document and doesn't know a paragraph break happened; chunk_paragraphs() flushes its buffer at every paragraph boundary (L104-106) before falling back to sentence-splitting.

Three real queries, four strategies, real scores

compare_retrieval() runs each query against all four indexes with n_results=1 — sharpest possible test: whose single best chunk wins. Fixed chunking never does.

Worth noticing, not yet proving Every one of this document's 5 source paragraphs is 282–460 characters — all longer than the 250-character cap. That means chunk_paragraphs()'s "merge short paragraphs together" branch (L109) and its "flush and start fresh" branch (L112-114) never fire on this input at all — every single output chunk comes from the "paragraph too big → fall back to sentences" branch (L102-108). What's actually winning here isn't merging; it's resetting the sentence accumulator at every paragraph boundary so a chunk can never blend two topics. On a document with genuinely short paragraphs, the other two branches would finally get exercised — and might tell a different story.

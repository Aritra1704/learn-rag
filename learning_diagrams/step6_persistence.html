Runs to a Reused Index

step6_persistent.py fixes two step-5 limits: the index lived only in memory, so every run re-embedded every chunk from scratch, and only one PDF could be indexed at a time. PersistentClient writes to disk; a manifest collection remembers which files are already in. Same three real PDFs as before — run twice, watch what changes.

Run it twice: full embed, then instant skip

First execution against a fresh ./chroma_db: three real PDFs, ten Ollama embedding calls, real wall-clock time per file. Second execution, same command, same folder: the manifest already knows all three files, so index_pdf() returns before touching Ollama at all.

Two small fixes doing the real work

Neither is complicated: a cheap fingerprint check answers "have I seen this file?", and a per-file id prefix answers "which file does chunk 3 belong to?" — the exact gap step 5's str(i) left open once a second document showed up.

One shared index, five real questions, three documents

This is what multi-document actually buys you: a single collection.query() against all 22 vectors, and each question's top hit still lands on the right source file — real scores from the run above.

Worth noticing, not yet proving index_pdf() calls collection.add() and only then mark_indexed() — L135-136. If the process dies in between (Ollama times out mid-batch, the machine loses power), the chunks are on disk but the manifest never finds out, so the next run sees is_indexed() == False and re-adds the same file under new ids: duplicate chunks, silently. And chunk boundaries here are still the same blind 500-character window from step 5 — it cuts ai_concepts.pdf after "and h" exactly as it cut sample.pdf, with no sense of where a sentence actually ends.
